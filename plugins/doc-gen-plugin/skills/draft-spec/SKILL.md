# 叩き台ジェネレーター

議論の出発点となる「叩き台」を素早く生成するスキル。

**設計方針**: 他のスキルとはフローが逆。「不明点ゼロまでヒアリングしてから書く」のではなく、**先にドラフトを出して、人間と一緒に練り上げる**。

- ヒアリングは最小限（バッチ1回まで）。足りない情報は**推測で埋めてよい**
- ただし推測した箇所は必ず `⚠️仮定:` マーカーで明示し、レビューで確定させる
- 決めきれない論点は「オープンクエスチョン」として列挙し、レビューの議題にする
- 叩き台が固まったら、本仕様化に適したスキルへの引き継ぎを提案する

**適するケース**: アイデア段階で形にしたい / チームに見せる最初の1枚が欲しい / 何から決めればいいか分からない / 完璧な仕様はまだ要らない

**適さないケース**: 実装直前で解釈の余地をなくしたい（→ detail-spec）、要件を厳密に定義したい（→ req-spec）

## ワークフロー

```
1. コンテキスト収集（最小限: AskUserQuestion 1バッチまで + コードベース自動調査）
   ↓
2. 叩き台を生成し、Write ツールで即書き出し（仮定マーカー付き）
   ↓
3. レビュー＆練り上げサイクル（オープンクエスチョンを一緒に潰す）
   ↓
4. 次のステップ提案（本仕様化するスキルへの誘導）
```

## Step 1: コンテキスト収集（最小限）

他スキルのような深掘りヒアリングは**行わない**。

1. ユーザーの依頼から「テーマ」「目的」が読み取れるか判断する
2. 読み取れない場合のみ、AskUserQuestion で**1バッチ（1〜3問）だけ**質問する:
   - 何の叩き台を作りますか？（機能 / 設計 / プロダクト / 運用ルールなど）
   - この叩き台で何を決めたいですか？（議論のゴール）
   - 対象のコードベースはありますか？（あればパス）
3. 対象コードベースがある場合、Glob/Grep/Read で技術スタック・既存パターンを**自動収集**する（ユーザーへの質問はしない）
4. **これ以上のヒアリングはせず、Step 2 に進む**。情報が足りない部分は推測で埋める

## Step 2: 叩き台生成

1. `assets/templates/draft.md` を Read ツールで読む
2. 収集したコンテキストと推測でテンプレートを埋める
   - **推測で埋めた箇所には必ず `⚠️仮定:` を付ける**（本文中にインラインで）
   - 仮定は「5. 前提と仮定」セクションにも集約し、確認方法を添える
   - 判断が分かれる論点は無理に1案に絞らず、案A/案Bの比較として提示してよい
   - 決めるべきことは「6. オープンクエスチョン」に列挙し、各項目に推奨案を添える
3. **不要なセクションは削除**、**必要なセクションは自由に追加**してよい
4. **Write ツールで即座に書き出す**。完成度6割で出してよい。レビューサイクルで練り上げるのが前提

## Step 3: レビュー＆練り上げサイクル

書き出したら、ユーザーにレビューを依頼する:

```
叩き台を {ファイルパス} に書き出しました。
⚠️仮定 が {N} 件、オープンクエスチョンが {M} 件あります。

一緒に練り上げていきましょう:
- 「仮定の◯番は合ってる / 違う。実際は〜」
- 「オープンクエスチョンの◯番は案Aで」
- 「〜のセクションを追加して / 削除して」
- 「OK」（この内容で確定）
```

### ルール

- 修正指示を受けたら Edit ツールで反映し、修正箇所を要約して報告
- 仮定が確定したら `⚠️仮定:` マーカーを外し、「5. 前提と仮定」から「確定事項」へ移す
- オープンクエスチョンが解決したら「6. オープンクエスチョン」から削除し、本文に反映する
- ユーザーが迷っている論点は、選択肢とトレードオフを提示して**一緒に考える**（急かさない）
- ユーザーが「OK」「これでいい」等と言うまで繰り返す

## Step 4: 次のステップ提案

確定後、残った仮定・オープンクエスチョンの件数を報告し、内容に応じて本仕様化のスキルを提案する:

| 叩き台の内容 | 提案するスキル |
|:------------|:-------------|
| プロダクト・要件寄り | req-spec（SRS / プロダクトブリーフ等） |
| アーキテクチャ・技術選定寄り | arch-spec（RFC / テクニカルデザイン等） |
| 機能単位の仕様 | feature-spec |
| 実装直前の詳細設計 | detail-spec（設計仕様書 / 実装仕様書） |
| API設計 | api-spec |

提案するだけでよい。ユーザーが望んだ場合のみ、該当スキルの利用を案内する。

## 出力先

**デフォルト出力先**: `docs/`
**カスタム出力**: ユーザーが指定した場合はそのパスを使用。

ファイル名: `docs/draft-{name}.md`
